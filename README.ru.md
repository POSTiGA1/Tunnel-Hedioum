Hedioum — это высокопроизводительный туннель-мультиплексор корпоративного уровня для **обхода блокировок и жёсткой цензуры (DPI)** и предотвращения «обвала» TCP под нагрузкой. Он заворачивает зашифрованный трафик VLESS/Trojan в динамически масштабируемые пулы соединений, которые носят **арсенал из 16 маскировок** — **SSH, TLS/HTTPS, почта (SMTP/IMAP/SMTPS/IMAPS), базы данных (PostgreSQL/MySQL) и панели хостинга/devops (cPanel, WHM, Webmail, DirectAdmin, Docker Registry, Grafana, Prometheus)** — собранных в цельные серверные **персоны**, поверх современного аутентифицированного шифрования. Также предоставляет опциональный **TUN-интерфейс** уровня ОС и **прозрачный режим шлюза**, и работает **на MikroTik/RouterOS и в Docker** — маршрутизируя целую LAN через замаскированный туннель без изменений на устройствах.

> Архитектура: клиент → панель Xray (внутри) → **хаб Hedioum (внутри)** → маскированный туннель → **зарубежный выходной узел** → свободный интернет.
> Токен создаёт выходной узел; сначала установите зарубежный узел, затем внутренний.

## 🌟 Ключевые возможности

- **Динамическая балансировка (Chaos Mesh):** вместо Round-Robin — алгоритм «наименее загруженного»; число физических соединений масштабируется по реальной полосе (Mbps), а не по числу потоков.
- **Обход DPI (плавающие лимиты):** каждое соединение работает под случайным плавающим лимитом полосы, разрушая статичные сигнатуры — трафик выглядит как обычный «шумный» интернет.
- **Слив без обрывов (Draining):** при масштабировании вниз простаивающее соединение переходит в состояние `Draining` и ждёт естественного завершения активных потоков — без лагов и разрывов для пользователя.
- **Аутентифицированное шифрование (ChaCha20-Poly1305):** транспорт защищён современным AEAD-потоком с ключом из вашего токена через HKDF. **Токен никогда не передаётся по сети** и одновременно является ключом шифра, поэтому пассивный наблюдатель видит лишь случайные соли и шифртекст.
- **Реальный сертификат (Let's Encrypt) или маскировка под DirectAdmin:** укажите домен (`--domain`) — и TLS-маскировка отдаёт **настоящий автопродлеваемый сертификат Let's Encrypt** (ACME, с предпроверкой A/AAAA, самовосстанавливающимся продлением и безопасным откатом на самоподписанный). Без домена используется самоподписанный. Узел также может носить **маскировку панели DirectAdmin**: пиксельно точную страницу входа *Evolution* на порту **2222** (светлая/тёмная тема, ресурсы встроены в бинарник), где самоподписанный сертификат является нормой.
- **Жизненный цикл соединений с учётом протокола:** после объёма данных сильнейший признак туннеля — «протокол × время жизни соединения». SSH — долгоживущий костяк; каждая не-SSH маскировка вспомогательна: случайное **время жизни 5–60 мин + лимит передачи 1–5 ГБ**, затем слив и замена на свежее соединение. Тайминги каждого сервера выводятся из его секретного токена, поэтому серверы не похожи друг на друга.
- **Полный TCP + UDP:** один локальный порт SOCKS5 обслуживает и TCP (CONNECT), и UDP (ASSOCIATE), поэтому работают QUIC/HTTP3, DNS и голосовые/видеозвонки. UDP идёт по отдельному под-пулу, изолированному от TCP; между узлами «голого» UDP нет — он туннелируется внутри маскированного TCP.
- **Опциональный IPv6:** межузловой канал и выход могут использовать IPv6 (`egress_ip_mode`: `ipv4` по умолчанию / `ipv6` / `dual`), не раскрывая IPv6-личность сервера по умолчанию.
- **Опциональный TUN + DNS без утечек:** помимо порта SOCKS5, каждый узел может предоставить **TUN-интерфейс** уровня ОС (`--tun`), чтобы туннель был доступен как обычный сетевой интерфейс, плюс **форвардер DNS на `:53`** (`--dns`), разрешающий имена через туннель (без локальной утечки). Это per-node (свой интерфейс + `/24`), опционально и **никогда не становится маршрутом по умолчанию** — так что собственный выход хаба и SSH остаются прямыми. TUN-движок (userspace-стек gVisor поверх SOCKS узла) не требует внешнего `ip`, поэтому работает и в контейнере `FROM scratch`.
- **Прозрачный режим шлюза (маршрутизация всей LAN):** с `--gateway` хаб — особенно единственный контейнер на **MikroTik/RouterOS** или любом Linux-маршрутизаторе — становится прозрачным L3-шлюзом: устройства LAN оставляют маршрутизатор своим шлюзом, вы **маркируете + маршрутизируете** нужный трафик на контейнер (точно паттерн WireGuard/L2TP), и целая LAN идёт через замаскированный туннель — **без изменений на устройствах и без внешнего прокси**. На движке TUN; маршрутизация через netlink (`iif`-правило + `ip_forward`) с защитой для RouterOS 7.22. **Проверено от начала до конца на настоящем RouterOS CHR и на обычном Linux-маршрутизаторе** (выходной IP клиента LAN = зарубежный, TCP+UDP, без утечек DNS, без блокировки доступа).
- **Работает на MikroTik / в Docker:** поставляется как крошечный мультиарх (`amd64/arm64/armv7`) образ `FROM scratch` (~17 МБ) на `ghcr.io/hedioum/pool-tunnel`, **проверено в контейнере RouterOS с работающими TUN и режимом шлюза** — см. пошаговое **[руководство по MikroTik](docs/MIKROTIK.ru.md)**.
- **Подключаемые маскировки — арсенал из 16:** один узел слушает сразу за многими масками. **SSH** (реальный баннер SSH-2.0, побайтово зеркалирующий `sshd` хоста); **implicit-TLS** на **TLS/HTTPS**, **HTTPS-alt (:8443)**, **SMTPS/IMAPS (465/993)**, **Docker Registry (:5000)**, **Grafana (:3000)**, **Prometheus (:9090)** и панелях **cPanel / WHM / Webmail** (`:2083/2087/2096`, настоящий заголовок сервера `cpsrvd` и пиксельно точные страницы входа); **STARTTLS** на **SMTP/IMAP (587/143)**, **PostgreSQL (:5432)** и **MySQL (:3306)** (настоящие прологи протокола — `SSLRequest`, приветствие MySQL v10 — до перехода на TLS); и панель **DirectAdmin** (:2222). Хаб распределяет соединения между ними с **уникальным для каждой установки плавающим распределением** (Chaos Mesh v2). Неавторизованные зонды направляются к правдоподобной приманке — реальный `sshd`, вход в настоящую панель или веб-персона, чьи заголовки `Server`/`ETag`/`Last-Modified` **уникальны для каждой установки**. На порту **80** тоже работает приманка, чтобы даже «голый» IP выглядел как обычный веб-хост.
- **Цельные серверные персоны:** вместо случайного набора масок узел может носить **персону** — самосогласованную личность, узнаваемую реальными админами: **`cpanel`** (TLS + cPanel/WHM/Webmail), **`directadmin`** (TLS + DirectAdmin) или **`devops`** (TLS + HTTPS-alt + Docker + Grafana + Prometheus). Каждая персона — это **SSH + 9 согласованных масок**, детерминированно порождённых из токена узла (так что хаб выводит тот же набор из общего токена), с правилом, что несовместимые панели не появляются вместе. Выбор: `--persona cpanel|directadmin|devops` или `--persona auto`.
- **Онбординг «вставь-и-готово» (pairing-токен v2):** `setup-foreign` печатает единый самодостаточный **pairing-токен** (base64url), уже содержащий IP выхода, все сопоставления маска→порт, персону и ключ — так что хаб настраивается вставкой одной строки: `setup-iran --token <PAIRING_TOKEN> --socks-port 40001`. Никаких ручных `--target-ip`/`--mimics`/`--persona`.
- **Многопортовая гонка подключения (connect-race):** хаб набирает узел по всем его портам-маскам взвешенной гонкой «сначала безобидные» с памятью доступности по каждому эндпоинту (cooldown/backoff); так что если один порт (например `:22`) на вашем пути заблокирован или throttled, туннель всё равно поднимется через остальные и восстановится сам.
- **Без утечки DNS по замыслу:** вход SOCKS5 передаёт в туннель **доменное имя** (а не локально разрешённый IP), поэтому DNS резолвится на **зарубежном узле** — настройте клиент на удалённый DNS (`domainStrategy: AsIs`).
- **Токен-аутентификация, привязанная к каналу (без двойного шифрования):** TLS-маскировка аутентифицирует пир через HMAC, привязанный к отпечатку живого сертификата сервера, **доказывая знание токена, но не отправляя его**, сохраняя **один** слой шифрования. Клиент использует **uTLS** (реальный Chrome ClientHello) против JA3-отпечатков.
- **Инженерия пропускной способности:** BBR + `fq` при установке, окна потоков Yamux расширены до 16 МБ, встроенные команды `speedtest` и `probe`.

## 🚀 Установка и обновление

Сначала установите **зарубежный (выходной) узел**, чтобы получить токен для внутреннего узла. Полное руководство — **[docs/DEPLOY.md](docs/DEPLOY.md)**.

### Установка одной строкой (если GitHub доступен)
На каждом VPS от root (сначала зарубежный):

    bash <(curl -fsSL https://raw.githubusercontent.com/hedioum/Hedioum-Pool-Tunnel/main/install.sh)

### Неинтерактивно (автоматизация)

    hedioum-tunnel install
    hedioum-tunnel setup-foreign --persona auto --move-ssh --domain vpn.example.com   # зарубежный; печатает pairing-токен
    hedioum-tunnel setup-iran   --alias DE-01 --token <PAIRING_TOKEN> --socks-port 40001   # вставьте токен; добавьте --tun --dns для TUN-интерфейса
    systemctl start hedioum.service

`--persona auto|cpanel|directadmin|devops` выбирает цельную личность (SSH + 9 масок); `--mimics all` (или список через запятую) тоже работает для явного набора. `setup-foreign` печатает самодостаточный **pairing-токен** — вставьте его в `setup-iran`, и IP выхода, порты и персона настроятся сами (без `--target-ip`/`--mimics`). `--domain` опционален (настоящий сертификат Let's Encrypt). На хабе добавьте `--tun` (и `--dns`), чтобы предоставить TUN-интерфейс + резолвер `:53` без утечек.

**Редактирование узла на месте** (меняются только переданные флаги; токен сохраняется, если нет `--token`/`--rotate-token`):

    hedioum-tunnel edit-foreign --tls-port 2087 --decoy-style directadmin   # на зарубежном
    hedioum-tunnel edit-node --alias DE-01 --bw 12                          # на внутреннем хабе

### Диагностика

    hedioum-tunnel probe     --node DE-01       # доступность каждой маскировки (хаб)
    hedioum-tunnel speedtest --node DE-01       # реальная пропускная способность выхода (хаб)
    hedioum-tunnel check-ip                     # репутация выходного IP: CLEAN / LIKELY-FLAGGED (зарубежный)

## ⚙️ Панель управления

В любой момент запустите интерактивную панель из терминала:

    hedioum-tunnel

Просмотр активных пулов и эндпоинтов по узлам, живые логи, динамическое **добавление/редактирование/удаление** узлов, speedtest / probe / check-ip, безопасное самообновление и полное удаление.

## 🐳 Docker и MikroTik

Hedioum поставляется как крошечный мультиарх (`amd64/arm64/armv7`) образ `FROM scratch`
(~17 МБ) на `ghcr.io/hedioum/pool-tunnel`. Запуск хаба в контейнере:

    docker run -d --name hedioum --restart unless-stopped \
      --cap-add NET_ADMIN --device /dev/net/tun \
      -v /etc/hedioum:/etc/hedioum ghcr.io/hedioum/pool-tunnel:latest

(Для режима только-SOCKS не нужны ни cap, ни device.) Сначала запишите конфиг разовым
запуском, напр. `docker run --rm -v /etc/hedioum:/etc/hedioum ghcr.io/hedioum/pool-tunnel:latest
setup-iran --alias FR --token <PAIRING_TOKEN> --socks-port 40001 --tun --dns`. В образе нет
shell, но любую подкоманду можно выполнить через `docker exec hedioum hedioum-tunnel test
--node FR` (speedtest, probe, edit-node, …); после правки конфига `docker restart hedioum`.

**На MikroTik/RouterOS** тот же образ работает в контейнере RouterOS — с работающими TUN и
**режимом шлюза**. Включите `--gateway`, затем на маршрутизаторе просто `mark` трафик и
`route` его на veth-IP контейнера, чтобы пустить **целую LAN** через туннель (без изменений на
устройствах). Полное пошаговое руководство с нуля: **[docs/MIKROTIK.ru.md](docs/MIKROTIK.ru.md)**.
